# Part 2 implementation notes

## Database and compatibility

- The API and MVC app target .NET 10; the API uses Entity Framework Core 10.
- `docs/database.sql` describes the clean-install schema. It drops and recreates
  tables, so do not run it against a database containing data you need.
- For an existing installation, use the application's configured database
  upgrade option only after backing up the database and reviewing the schema
  changes.
- Passwords are stored as PBKDF2-SHA256 hashes generated by the API; do not
  insert plaintext example passwords. Create accounts through registration.
- Result rows are unique per registration. The API validates result status,
  position, and time before persisting a result.

## Azure and tests

- Image uploads use Azure Blob Storage configured by
  `AzureBlobStorage:ConnectionString` and `AzureBlobStorage:ContainerName`.
- The upload validator accepts JPG, PNG, WEBP, and GIF files up to 5 MB.
- API integration tests replace blob storage with a fake and do not require
  Azure credentials.
- Configure local secrets outside source control. Docker Compose reads local
  settings from `.env`; `.env.example` contains placeholders only.

## Design changes from Part 1

Part 2 adds event distance in kilometres and banner URLs, participant profile
picture URLs, event type and category price. Event, category, and result
validations now enforce the business rules described in
[the endpoint plan](API-Endpoint-Plan.md). Cancelled enrolments do not count
towards capacity; events and categories with enrolments cannot be deleted.

The API keeps the existing registration routes while also exposing enrolment
aliases. Weather routes operate on saved weather data and do not retrieve live
forecasts from an external provider.
